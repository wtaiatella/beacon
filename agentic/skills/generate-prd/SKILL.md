# Generate PRD

## When to Use

- Creating a new product requirements document from scratch
- Updating an existing prd.md with new requirements
- Analyzing attachments (PDFs, docs) to extract requirements
- Any time `/prd` needs to produce or modify prd.md file

Output format is **normative**: follow section order exactly.

## Output Location and Naming

- **Directory:** `docs/specs/{slug}/` (folder for this workflow)
- **Filename:** `prd.md` (always this name)
- **Metadata:** `_state.json` + `_notes.md` in same folder (tracks workflow status — schema and
  convention owned by the `bcs-ticket-workflow` skill; this is the only control-file convention)

## Folder Structure

```
docs/specs/{slug}/
├── prd.md              (generated by /prd)
├── spectech.md         (generated by /spectech)
├── tasks.md            (generated by /tasks)
├── repro.md            (optional: from /bcs-repro — read before drafting when present)
├── repro-fixtures/     (optional: durable ticket fixtures pending promotion into repo test/)
├── _state.json         (metadata, updated by each step — see bcs-ticket-workflow skill)
├── _notes.md           (human-readable running log — see bcs-ticket-workflow skill)
└── attachments/        (optional: PDFs, images, docs)
```

## PRD Template (Required Order)

### 1. Header with Metadata

```markdown
---
name: {slug}
created: {YYYY-MM-DD}
last-updated: {YYYY-MM-DD}
status: draft
workflow: prd-done
---
```

- `name`: slug of project/task
- `created`: first creation date
- `last-updated`: when last modified
- `status`: draft | in-progress | approved
- `workflow`: prd-done (set by /prd), spectech-done (set by /spectech), tasks-done (set by /tasks)

### 2. Title (H1)

Clear, concise feature or project name.

### 3. ## Overview

1-2 paragraphs: What is being built, why it matters, who benefits.

### 4. ## User Stories (Prioritized)

Recommended for every PRD. Each story is an **independently testable, MVP-sized slice** —
implementing just one still delivers usable value. Assign a priority (P1 = most critical);
the P1 stories define the MVP. Order the section by priority.

Format:
```
**US-1: Start Free Trial** (Priority: P1)
- As a: potential customer
- I want to: start a free trial without providing payment info
- So that: I can test the service risk-free

**Why this priority:** blocks all conversion — nothing ships without it.
**Independent Test:** sign up with email only and confirm an active 14-day trial;
delivers value even if no other story is implemented.

Acceptance Scenarios:
- **Given** a visitor with a valid email, **When** they submit signup, **Then** a 14-day trial is created with no payment method required.
- **Given** an active trial, **When** the user opens their dashboard, **Then** the remaining trial days are shown.
```

- Each story must be independently developable, testable, and demonstrable.
- If the request spans multiple independent subsystems, do **not** cram them into one story set — flag for decomposition (see the `/prd` workflow) before refining.

### 5. ## Functional Requirements

Clear, numbered list of what the system must do. Each **FR must be testable**:
- FR-1: User can start a 14-day free trial without a credit card
- FR-2: User can view trial status and days remaining
- FR-3: System sends a notification before the trial ends
- etc.

Mark genuinely critical unknowns inline with a `[NEEDS CLARIFICATION: <question>]` marker
(see the clarification budget in **Notes**) rather than guessing silently:
- FR-4: System retains trial data for [NEEDS CLARIFICATION: retention period not specified]

### 6. ## Acceptance Criteria

Verifiable conditions in **Given/When/Then** form — each scenario is a potential test case.
No vague language ("user can easily", "system should handle"):

- **AC.1: Given** a visitor on the landing page, **When** they start a trial, **Then** the trial activates within 30 seconds.
- **AC.2: Given** a new trial, **When** the welcome email is sent, **Then** it contains the start and end dates.
- **AC.3: Given** a trial 3 days from expiry, **When** the daily job runs, **Then** a billing-reminder notification is sent once.
- **AC.4: Given** an active trial, **When** the user cancels in account settings, **Then** the trial is marked cancelled and no further notifications are sent.

### 7. ## Success Criteria

**Measurable, technology-agnostic** outcomes stated from the user/business perspective.
No frameworks, languages, databases, or internal-latency numbers here — those belong in
spectech.md. Each criterion must be verifiable without knowing the implementation:

- SC-1: Users can complete trial signup in under 2 minutes.
- SC-2: 95% of trial activations succeed on the first attempt.
- SC-3: The system supports 10,000 simultaneous active trials without degradation.
- SC-4: Trial-related support tickets drop by 40% within one quarter.

Good vs. bad:
- ✅ "Users see trial status instantly" / ❌ "API response time under 200ms" (implementation-level)
- ✅ "Supports 10K concurrent trials" / ❌ "Database sustains 1000 TPS" (technology-specific)

### 8. ## Scope

What IS included:
- Free trial signup (no payment)
- Trial status display
- Expiration notification
- Cancellation

What IS NOT included (explicitly):
- Paid conversion (Phase 2)
- Auto-renewal (Phase 2)
- Multiple trials per account (Phase 2)

### 9. ## Non-Functional Requirements (Optional)

Performance, availability, security at business level:
- Trial must start within 30 seconds of signup
- Notification must send within 24 hours of trigger
- System must support 10K simultaneous trials

### 10. ## Dependencies

External services, integrations, blockers:
- Stripe API (for customer data, not payments yet)
- Email service (notification delivery)
- Database (trial status tracking)

### 11. ## Assumptions

Facts assumed to be true, **including every informed default chosen when the request was
silent** and each resolved clarification. Recording the assumption is what lets `/prd`
proceed without stalling on a question:
- User has a valid email address
- Trial duration defaults to 14 days (industry standard; not specified by client)
- Email delivery SLA is 99%
- [Resolved] Trial expiration is calculated in the user's local timezone (per clarification 2026-07-12)

### 12. ## Deferred Questions (Optional)

Only for genuinely **non-blocking** items intentionally postponed. Critical unknowns must
instead be inline `[NEEDS CLARIFICATION]` markers and resolved via the clarification loop —
do **not** park scope/security/UX-affecting decisions here:
- Should trials be geo-specific? (revisit in Phase 2)
- Refund policy if a customer converts to paid early? (business input pending)

### 13. ## Attachments Referenced

List files in `attachments/` that were processed:
- `wireframes.pdf` — UI mockups
- `requirements.pdf` — client requirements
- `api-contract.json` — integration spec

### 14. ## Reproduction Evidence & Required Integration Tests

**When `repro.md` exists** in the ticket folder (produced by `/bcs-repro`), this section is
**mandatory**. Read `repro.md` (especially **Input kind**, **Fixture resolution**, and
**Required integration tests**) and promote them into the PRD so `/spectech` → `/tasks` → `/dev`
implement durable integration coverage — not ephemeral Mongo-only overlays.

If `repro.md` is missing, omit this section and note in Assumptions that no local repro ran yet
(or that repro was blocked).

Template:

```markdown
## Reproduction Evidence & Required Integration Tests

- **repro.md:** `docs/specs/{slug}/repro.md`
- **Sandbox scenario:** engine | swagger | ui
- **Input kind(s):** HTTP payload | invoice/XML | DB records (citations/…) | auth context | UI sequence | …
- **Fixtures (durable paths in-repo):**
  - reused: `path/to/existing…` (overrides: …)
  - created: `path/to/BG-XXXX-…` (isolation: …)
- **Load procedure:** how fixtures are applied on top of `/bcs-sandbox --seed` (summary; details in repro.md)
- **Canonical call(s):** method, URL/query, headers summary, or UI path
- **Observed before fix → required after fix:** one line per call (from repro.md)
- **Required integration tests** (normative for `/tasks` / `/dev` — copy/adapt IT-* from repro.md):
  - **IT-1:** …
  - **IT-2:** …
- **Owning suite hint:** e.g. `hoplias/test/configurations/…`
```

Rules:
- Prefer **paths to versioned fixtures** over describing documents only in prose.
- New fixtures described here must be **realistic / client-like** (not toy `XX`/`YY`/`ZZ` keys);
  note any synthetic isolation field and why.
- Each IT item must be independently implementable as an automated test that loads those fixtures
  and asserts the after-fix behavior.
- Do **not** invent alternate seed data here — stay faithful to `repro.md`. Technical suite wiring
  details beyond the hint belong in spectech/tasks.

## Quality Bar Before Handoff

- [ ] All sections present in order
- [ ] User stories are prioritized (P1/P2/P3) and each has an Independent Test
- [ ] Acceptance criteria use Given/When/Then and are testable
- [ ] Success criteria are measurable and technology-agnostic
- [ ] No unresolved `[NEEDS CLARIFICATION]` markers remain (resolved into Assumptions or answered)
- [ ] Scope clearly defines in/out
- [ ] No technical implementation details (that's spectech.md job)
- [ ] If `repro.md` exists: section 14 present and IT-* items mapped from it
- [ ] PRD answers: What is being built? Why? For whom?
- [ ] File saved to `docs/specs/{slug}/prd.md`
- [ ] `_state.json.steps.prd` updated to `"done"` (validation outcome recorded there too) and a
      matching `_notes.md` entry appended — per the `bcs-ticket-workflow` skill (the only
      control-file convention; no other metadata file is created)

## Notes

- **Focus on WHAT, not HOW** — leave technical decisions for spectech.md
- **Be specific** — "user can start free trial" is vague; "user can start 14-day free trial without payment method" is clear
- **Make informed guesses, then document them** — when the request is silent, choose a
  reasonable industry-standard default and record it in **Assumptions** instead of stalling.
  Reserve `[NEEDS CLARIFICATION: <question>]` markers for decisions that truly can't be
  defaulted, with a **hard budget of 3** and this priority order:
  **scope > security/privacy > user experience > technical detail.** The `/prd` clarification
  loop resolves these before handoff.
- **Reference attachments** — if you analyzed a PDF, cite it: "per requirements.pdf, users must complete onboarding step"
- **Keep it readable** — short paragraphs, bullet lists, clear language
